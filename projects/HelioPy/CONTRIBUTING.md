# Руководство для контрибьюторов HelioPy

Спасибо за интерес к HelioPy! Мы приветствуем вклад от сообщества.

## Как внести вклад

### Сообщение об ошибках

Если вы нашли баг:
1. Проверьте, не была ли уже создана такая issue
2. Создайте новую issue с детальным описанием:
   - Шаги для воспроизведения
   - Ожидаемое поведение
   - Фактическое поведение
   - Версия Python и HelioPy
   - Traceback (если есть)

### Предложение новых функций

Для предложения новой функциональности:
1. Создайте issue с описанием:
   - Зачем это нужно
   - Как это должно работать
   - Примеры использования
2. Дождитесь обсуждения перед началом работы

### Pull Requests

1. **Fork и клонирование**
   ```bash
   git clone https://github.com/your-username/heliopy.git
   cd heliopy
   ```

2. **Создание виртуального окружения**
   ```bash
   python -m venv venv
   source venv/bin/activate  # Linux/MacOS
   venv\Scripts\activate     # Windows
   ```

3. **Установка в режиме разработки**
   ```bash
   pip install -e .
   pip install -r requirements/dev.txt
   ```

4. **Создание ветки**
   ```bash
   git checkout -b feature/my-new-feature
   ```

5. **Внесение изменений**
   - Пишите чистый, читаемый код
   - Следуйте PEP 8 (используйте black для форматирования)
   - Добавляйте docstrings для публичных функций/классов
   - Пишите тесты для нового кода

6. **Запуск тестов и линтеров**
   ```bash
   # Форматирование кода
   black heliopy/ tests/
   
   # Проверка стиля
   ruff check heliopy/
   
   # Запуск тестов
   pytest
   
   # Проверка покрытия
   pytest --cov=heliopy
   ```

7. **Commit и Push**
   ```bash
   git add .
   git commit -m "Описание изменений"
   git push origin feature/my-new-feature
   ```

8. **Создание Pull Request**
   - Опишите, что изменено и зачем
   - Укажите связанные issues
   - Убедитесь, что все тесты проходят

## Стандарты кода

### Стиль кода
- Используйте **black** для форматирования (line-length=100)
- Следуйте **PEP 8**
- Используйте **type hints** где возможно
- Пишите понятные имена переменных и функций

### Документация
- Все публичные функции/классы должны иметь docstrings
- Используйте формат NumPy для docstrings
- Пример:
  ```python
  def my_function(param1: int, param2: str) -> bool:
      """
      Краткое описание функции.

      Детальное описание того, что делает функция.

      Parameters
      ----------
      param1 : int
          Описание первого параметра.
      param2 : str
          Описание второго параметра.

      Returns
      -------
      bool
          Описание возвращаемого значения.

      Examples
      --------
      >>> my_function(42, "hello")
      True
      """
      return True
  ```

### Тесты
- Пишите unit-тесты для всего нового кода
- Используйте pytest
- Стремитесь к покрытию > 80%
- Тесты должны быть:
  - Быстрыми
  - Изолированными
  - Воспроизводимыми
  - Понятными

### Commit-сообщения
Используйте четкие и описательные commit-сообщения:
```
Краткое описание (до 50 символов)

Более детальное объяснение, если необходимо.
Разделите абзацы пустой строкой.

- Используйте маркированные списки для перечислений
- Укажите связанные issues: Fixes #123
```

## Процесс ревью

1. Maintainer проверит ваш PR
2. Могут быть запрошены изменения
3. После одобрения PR будет смержен
4. Ваше имя будет добавлено в список контрибьюторов

## Вопросы?

Если у вас есть вопросы, создайте issue с тегом "question".
